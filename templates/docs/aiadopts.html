Clients & Users ›Client ID & Users

Client ID & Users

Every user in AI Adopts belongs to a Client (organization). The ClientUserInfo model is the central governance record that controls what each client's users can see and do.

Core Concept

A Client is an organization subscribing to Library Bot. A User is an individual within that client. User-level access and feature visibility are both derived from the client's configuration.

📌 Key RuleUsers are always scoped to their client. Cross-client data leakage is prevented at the queryset level in all APIs.

User Identity Resolution

When a user makes a request, the following resolution happens:

1
Auth Token → User

Bearer token resolves to a user identity

2
User → Client mapping

Via User.get_client() → ClientUserInfo

3
Client → LibraryBotConfig

Feature flags, buttons, permissions resolved

4
Context passed to frontend

userInfo object consumed by UserContext provider

Client User Information API

GET /api/v1/accounts/client-user-information/

Resolves client config, feature flags, and the LibraryBotConfig for the authenticated user's client. Called on app bootstrap.

UI Impact: Determines which buttons show, whether login is required, which bots are available, and feature visibility (AI Pulse, Leaderboard, Transform IQ).

Response (key fields)

Field Type Description
client_name string Client identifier used in all API calls
member_emails array All user emails in this client
libraryBotConfig object Feature flags, bot config, UI controls
collections array Curated concept collections for this client

User Account API

GET /api/v1/accounts/

Returns user identity and client mapping. Used by UserContext to populate the user object.

Adding & Removing Users

✅ How it worksUsers are associated via member_emails on ClientUserInfo. Email match = access granted.
Action Mechanism Effect
Add User Append email to member_emails in admin User gains access on next login
Remove User Delete email from member_emails User loses access; excluded from all reports
Feature toggle Update libraryBotConfig flags Changes UI buttons, visible sections, bots

Tenancy › Concept of Tenants

Concept of Tenants

AI Adopts is a multi-tenant platform. Every client is an isolated tenant — they share the same codebase but have completely independent data, configurations, and users.

What is a Tenant?

A tenant maps directly to a Client. The tenant is resolved from every authenticated request via middleware.

🔐 Tenant Resolution FlowAuth Token → Middleware → Client/Tenant context → All querysets automatically scoped

Tenant Isolation Rules

Layer Isolation Mechanism
Data All querysets filtered by client/tenant identity
Users Scoped via member_emails on ClientUserInfo
Course Packages Each CoursePackage FK'd to a ClientUserInfo
Reports AI Pulse & Leaderboard scoped to client members only
Company IQ approved=True + deleted=False enforced globally
CoachBot botId sourced from client-specific config

LibraryBotConfig — Tenant Feature Flags

The LibraryBotConfig model controls the exact experience each tenant gets. It is the primary feature-gating mechanism.

bot_configJSONWhich CoachBot(s) are available, their IDs and modes
feature_and_button_controls.ai_pulse_button.showBooleanWhether AI Pulse report section is visible
feature_and_button_controls.leaderboard_button.showBooleanWhether Leaderboard report is visible
leaderboard_report_protectedBooleanWhether Leaderboard requires a password
feature_and_button_controls.transform_iq_feature.showBooleanControls Transform IQ section visibility
feature_and_button_controlsJSONFine-grained feature/button show/hide

CoursePackage — Tenant Content Bundles

Each tenant gets one or more CoursePackages — client-specific bundles of courses. A package is the top-level unit that users see in the Library UI.

page_config example 
{
  "show_filters": "Industry, Function, Business Outcome",
  "show_lists": true,
  "show_search": true
}

The page_config JSON drives which filters and controls appear on the Library page — different per client, without code changes.

Tenant API Pattern

All tenant-aware APIs follow the same pattern:

1
Auth token verified

Middleware validates and extracts tenant identity

2
Queryset scoped

deleted=False + tenant FK filters applied at ORM level

3
Soft deletion respected

No hard-deletes — records marked deleted=True are invisible

4
Response serialized

Public serializer strips admin-only fields before response

Tenancy (Platform Access) ›Login vs No-Login Tenant

Login vs No-Login Tenant

AI Adopts supports two tenant access modes: authenticated (login required) and public (no login). These modes determine what features are available and how progress/analytics are tracked.

Access Modes

Feature Login Tenant No-Login Tenant
User identity ✅ Resolved via auth token ❌ Anonymous / email-based
Progress tracking ✅ Persisted to DB ❌ Disabled (onlyClientSetup=true)
Audio tracking ✅ played_audio + completion% ❌ Not persisted
AI Pulse Report ✅ Real member data ❌ No member scoping
Leaderboard ✅ Ranked by completion ❌ Not applicable
JobAid sessions ✅ Stored with user email ✅ Stored with provided email
IdeaBoard voting ✅ User email tracked ✅ Provided email tracked
CoachBot ✅ Full conversation history ⚠️ Limited per config

The onlyClientSetup Flag

The onlyClientSetup boolean prop on BookPageClient is the primary toggle for no-login mode:

TypeScript 
// Login tenant (default)
<BookPageClient id="pkg_123" />

// No-login tenant
<BookPageClient id="pkg_123" onlyClientSetup={true} />

Audio Tracking in Login Mode

When onlyClientSetup === false (login mode), audio playback fires a real-time progress update:

POST /api/v1/courses/course-progress
JSON Payload 
{
  "user_uid": "user_uid",
  "course_id": "course_uid",
  "module": {
    "module_id": "module_uid",
    "status": "in_progress",
    "completed_in_percentage": 45,
    "played_audio": 30
  }
}

In no-login mode, this API call is skipped entirely — no progress is persisted.

Authentication API

GET /api/v1/accounts/

Used by UserContext to resolve user identity. In no-login tenants, this may return a client-scoped anonymous session rather than a personal user record.

⚠️ No-Login tenantsJobAid sessions still store the email provided at submission time. This enables basic tracking without authentication.

How it works

Each Collection has action_tab_info JSON that defines buttons and their action keys. These actions match CaseMappings.action_name, which opens the embedded content.

How the Dashboard Connects

Every visible element in the Library Bot UI traces back to a record in the Django admin. The diagram below shows the chain of control:

Control chain 
Django Admin
│
├── ClientUserInfo          → Who can log in & what client they belong to
│   └── LibraryBotConfig    → Which sections / buttons / bots are ON or OFF
│
├── CoursePackage           → What content bundle the client sees
│   └── Course → Module     → Individual learning units (books, audio, tests)
│
├── Collection + CaseMappings → Concepts tab content (PDFs, iframes, job aids, system)
│

│
└── CompanyIQ               → Landscape tab company records (approve/reject)
✅ Golden ruleIf something is not showing up in AI Adopts, check the Django admin first — a missing FK, an approved=False flag, or a missing config field covers 90% of issues.

Client & User Management

Go to Admin → Accounts → ClientUserInfo

Client User Info Overview

The Client User Info section is designed to manage client accounts, control access, and customize branding and UI settings.

Client Management

  • Create new clients — set client_name (lowercase slug, unique)
  • Assign course packages
  • Assign Owner ID — must match an existing user

Access Control

  • Member Emails — grant access by adding emails
  • Domain Restrictions — allow only approved email domains

Login View Configuration

  • No Login — direct access without authentication
  • Email + Password — one-time access password → personal password setup
  • Only Email — access restricted to registered member emails

Other Config Fields

  • Default Filter — pre-configured filters auto-applied on load
  • Feature & button controls — show/hide buttons in the interface
  • Announcements — banner with text, links, heading/subheading
  • Feature boxes — feature labels for visual branding
  • Card button config — control visibility and labels of action buttons on cards
  • Leaderboard settings — optional password protection
  • Client logo — upload to customize the main interface
  • Collections — create in the Collection section first, then assign here

Creating a New Client

1
Add a ClientUserInfo record

Set client_name — this becomes the tenant identifier used in all APIs. Must be unique and lowercase-friendly.

2
Add member emails

Paste all user emails into member_emails. These are the only emails that will resolve to this client on login.

3
Link a LibraryBotConfig

Create or assign a LibraryBotConfig record. This is what gates every UI feature. Without it, the Library Bot loads with all features OFF.

4
Link a CoursePackage

Assign the content bundle for this client. The package controls which courses and modules they can access.

5
Assign Collections (optional)

Add curated concept collections for the Concepts tab. Without these, the Concepts section will be empty.

6
Resources (optional)

Add curated resources for the Resources tab. Without these, the Resources section will be empty.

Adding & Removing Users

Action Where in Admin Field to edit Effect
Add a user ClientUserInfo → edit member_emails — append email User gets access on next login
Remove a user ClientUserInfo → edit member_emails — delete email User loses access; excluded from all reports
Move user between clients Both ClientUserInfo records Remove from old, add to new Context switches on next session
Disable a client ClientUserInfo → edit Set deleted=True All users lose access immediately
⚠️ Important: member_emails is also what scopes the AI Pulse Report and Leaderboard. If a user's email is missing from the list, they won't appear in any analytics even if they're using the platform.

Tab Type Reference

Tab Type Behaviour When to Use
normal Custom CaseMappings are attached to this collection. Button actions must use the CONCEPTS_ prefix. When you want fully custom embedded content (PDF, HTML, iframe)
system Uses predefined system tabs. No CaseMapping required. Button types can be JobAid, Only Iframe, or Normal with a custom action name. When using built-in system functionality like AI Case Collection, JobAids, or iframes

Action Button Types

Each pillar can have multiple action buttons. Every button has a Label, an Action Name, and a Type:

Button Type Action Name Value Description
normal Custom action name (e.g. AI_CASE_COLLECTION) Custom tabs defined by the user. Used for specific use cases like AI Case Collections.
job_aid JobAid UID (e.g. jobaid_abc123) Links to a JobAid form. Used for guidance or support-based content. Put the exact JobAid UID in the action name.
only_iframe Name/title of the iframe (e.g. My Dashboard) Embeds external content directly via iframe. Put the iframe title as the action name.
📌 Multiple ButtonsYou can create multiple buttons within a single Collection using the same configuration structure. Each button has its own Label, Action Name, and Type — independently configurable.

Case Mapping — 4 Configuration Patterns

CaseMappings control what content appears when an action button is clicked. The correct setup depends on the Tab Type and Button Type combination:

Case 1 tab_type = system, button_type = normal
No CaseMapping needed. Set a custom action name for a specific use case (e.g. AI_CASE_COLLECTION). The system handles rendering internally.
Case 2 tab_type = system, button_type = job_aid
No CaseMapping needed. Set action_name to the exact JobAid UID. The system will load the JobAid form directly.
Case 3 tab_type = normal, button_type = normal
CaseMappings must be attached. The action_name in CaseMapping must follow the CONCEPTS_ prefix convention (e.g. CONCEPTS_DESIGN_GUARDRAILS). Each CaseMapping links to an embedded resource (PDF, HTML, iframe).
Case 4 tab_type = system, button_type = only_iframe
No CaseMapping needed. Set action_name to the iframe title/name. The system will embed the iframe directly when the button is clicked.
⚠️ CONCEPTS_ prefix ruleOnly Case 3 (tab_type = normal, button_type = normal) requires CaseMappings. In this case, every action_name in the CaseMapping must start with CONCEPTS_ — otherwise the button click will not load the correct content.
💡 Quick decision guide — No CaseMapping needed for Cases 1, 2, and 4 (all system tab types). CaseMapping is only required for Case 3 (normal tab type with normal button type).
